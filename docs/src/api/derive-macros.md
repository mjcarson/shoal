# Derive Macros

Roughly half of what runs at query time does not exist as source in this repository. It is
generated by `shoal-derive` from three macros. If you are trying to follow a query and lose
the thread, it is almost certainly because you have walked into generated code.

`cargo expand` is the tool for this:

```bash
cargo expand --example tmdb > /tmp/expanded.rs
```

## The three macros

| Macro | Applied to | Generates |
| --- | --- | --- |
| `#[derive(ShoalSortedTable)]` | A row struct | Query structs and trait impls for a sorted table |
| `#[derive(ShoalUnsortedTable)]` | A row struct | The same for an unsorted table |
| `#[db]` | The database struct | `TableNames`, `*Client`, `QueryKinds`, `ResponseKinds`, and the `ShoalDatabase` impl |

## Field attributes

```rust
#[derive(Debug, Archive, Serialize, Deserialize, Clone, ShoalSortedTable, DeepSizeOf)]
#[rkyv(derive(Debug))]
#[shoal_table(db = "TestDb")]
pub struct TestRecord {
    #[shoal(partition)]
    pub partition_key: String,
    #[shoal(sort)]
    pub sort_key: String,
    #[shoal(update)]
    pub data: String,
}
```

`shoal/tests/persistent_sorted_table.rs:17-32`

| Attribute | Meaning |
| --- | --- |
| `#[shoal(partition)]` | Part of the partition key. At least one required. Multiple are combined into a tuple. |
| `#[shoal(sort)]` | Part of the sort key. Required for sorted tables, forbidden on unsorted. |
| `#[shoal(filter)]` | Usable in a filter predicate and in a SHQL `WHERE`. |
| `#[shoal(update)]` | Usable in an update query. |

Parsed by `darling` into `ShoalField` (`shoal-derive/src/tables.rs:11-30`). Attributes
combine: a field can be both `filter` and `update`.

`#[shoal_table(db = "...")]` names the database this table belongs to. It must match the
`#[db]` struct's name exactly — it is used to construct identifiers like `TestDbClient` and
`TestDbQueryKinds` (`shoal-derive/src/lib.rs:76-82`).

The derive also requires the usual rkyv derives plus `Clone`, `Debug`, and
`DeepSizeOf` — `ShoalTableSupport` bounds all of them (`shoal-core/src/shared/traits.rs:392-400`).

### Compile-time validation

The macros panic during expansion on:

| Condition | Message | Location |
| --- | --- | --- |
| No partition key (sorted) | `Sorted tables require at least one partition key to be set!` | `shoal-derive/src/lib.rs:63-65` |
| No sort key (sorted) | `Sorted tables require at least one sort key to be set!` | `lib.rs:66-69` |
| No partition key (unsorted) | `Unsorted tables require at least one partition key to be set!` | `lib.rs:163-166` |
| `#[shoal(sort)]` on unsorted | `Unsorted tables do not support sort keys!` | `lib.rs:149` |
| Both partition and sort | `Fields cannot be both partition and sort keys!` | `lib.rs:50`, `:151` |
| Not a struct | `Only structs are currently supported` | `lib.rs:23-26` |
| Tuple or unit struct | `ShoalTable requires named fields` | `lib.rs:28-31` |

These are `panic!`s, not `syn::Error`s, so they surface as a proc-macro panic without a
useful span. `#[db]` does it properly, emitting `to_compile_error()`
(`lib.rs:218-225`) — worth copying to the derives.

## What a table derive generates

For a table `Movie`, from `shoal-derive/src/lib.rs:85-112`:

```
Movie
├── MovieGet          — a get query        (structs/get.rs)
├── MovieExists       — an exists query    (structs/get.rs)
├── MovieUpdate       — a client update    (structs/update.rs)
├── MovieUpdateData   — the server-side update payload (no keys)
├── MovieDelete       — a delete query     (structs/delete.rs)
├── MovieFilter       — a filter predicate (structs/filter.rs)
└── impls:
    ├── RkyvSupport
    ├── PartitionKeySupport      — name(), get_partition_key(), ...
    ├── TableSchemaSupport       — field roles and type validators, for SHQL
    ├── TableRowFormat           — headers()/row_values(), for shoalctl
    ├── ShoalTableSupport        — is_filtered / is_filtered_archived
    ├── ShoalSortedTable | ShoalUnsortedTable
    └── FromShoal<DbClient>      — response downcasting
```

### Get and Exists

```rust
pub struct MovieGet {
    pub partition_key: u64,
    pub filters: Option<MovieFilter>,
    pub limit: Option<usize>,
}

impl MovieGet {
    pub fn new(id: u64) -> Self { ... }
}
```

`shoal-derive/src/structs/get.rs:52-76` (unsorted form)

The partition key type is the field's type when there is one partition field, or a tuple when
there are several (`structs/get.rs:24-32`). So `MovieGet::new` takes the partition fields by
name and value, and the hashing to a `u64` happens inside.

Sorted gets take a `Vec` of partition keys, since a sorted get may span partitions
(`structs/get.rs:add_sorted`).

`limit` is generated on both, and — for sorted tables — ignored by the server
([Query Execution](../tables/query-execution.md#what-a-get-actually-filters-on)).

### Update and UpdateData

Two update types exist for one reason: the wire type carries the keys, the stored type does
not.

- `MovieUpdate` — what a client builds: partition key, sort key (if any), and the changed
  fields.
- `MovieUpdateData` — what goes into an intent log record: just the changed fields.

`ShoalTableSupport` names both (`shoal-core/src/shared/traits.rs:401-405`). Keeping keys out
of `UpdateData` matters because update intents are written for every update and the keys are
already implied by the partition being written to.

Update fields are wrapped in `Option`, so an update carries only what it changes.

### Filter

`MovieFilter` gets one optional field per `#[shoal(filter)]` field, and two evaluators:

```rust
fn is_filtered(filter: &Self::Filters, row: &Self) -> bool;
fn is_filtered_archived(filter: &Self::Filters, row: &<Self as Archive>::Archived) -> bool;
```

`shoal-core/src/shared/traits.rs:410-427`

The archived variant is what allows filtering without deserializing
([Partitions](../tables/partitions.md#maybeloaded)). Both are generated from the same field
list (`shoal-derive/src/tables.rs:39-60`) so they stay in step.

Filters are conjunctive equality only: every `Some` field must match. No ranges, no `OR`, no
negation.

### TableSchemaSupport

```rust
pub trait TableSchemaSupport {
    fn get_field_validator(field_name: &str) -> Option<TypeValidator>;
    fn get_field_role(field_name: &str) -> Option<FieldRole>;
    fn field_names() -> Vec<&'static str>;
}
```

`shoal-core/src/shared/traits.rs:367-377`

Reflection for SHQL: given a field name from a `WHERE` clause, is it a partition key, a sort
key, or a filter, and does the supplied literal deserialize into its type? Validators are
built with `make_validator::<T>()`, which closes over `serde_json::from_value::<T>`
(`shoal-core/src/shared/queries/parser.rs:55-61`). This is why table field types must
implement `serde::DeserializeOwned` for SHQL to work on them.

## What `#[db]` generates

```rust
#[db]
pub struct TestDb {
    pub test_records: PersistentSortedTable<TestRecord, FileSystem>,
}
```

`shoal/tests/persistent_sorted_table.rs:50-54`

### Step 1: rewrite the field types

`utils::rewrite_table_fields` (`shoal-derive/src/lib.rs:237`) turns

```rust
PersistentSortedTable<TestRecord, FileSystem>
```

into

```rust
PersistentSortedTable<TestRecord, FileSystem<TestDb>, TestDbTableNames>
```

This exists to break a circularity: the storage engine is generic over the database
(`FileSystem<D: ShoalDatabase>`), and the database is composed of tables that are generic over
the storage engine. Writing it out by hand means naming `TestDb` inside its own definition.
The macro fills in the self-reference.

The comment in `PersistentUnsortedTable::new` is candid about it:

> The double TableNames is strange but its an easy way to work around an issue where I could
> have cyclical generics (The table type requires itself as its own generic).

`shoal-core/src/server/tables/persistent/unsorted.rs:120-122`

### Step 2: emit the supporting types

From `shoal-derive/src/lib.rs:250-262`:

| Generated | From | Purpose |
| --- | --- | --- |
| `TestDbTableNames` | `traits/table_name.rs` | A `Copy` enum, one variant per table, named after the *row* type. Used as a map key everywhere. |
| `Display for TestDbTableNames` | `traits/display.rs` | Logging. |
| `impl ShoalDatabase for TestDb` | `traits/db.rs` | The dispatch layer. |
| `TestDbClient` | `structs/client.rs` | The client-side `QuerySupport` impl. |
| `TestDbQueryKinds` / `TestDbResponseKinds` | `structs/query_kinds.rs` | Wire enums, one variant per table. |
| `From` impls | `traits/from_query.rs` | So `client.send_one(row)` works without manual wrapping. |

Variant names come from the *inner row type*, not the field name
(`shoal-derive/src/utils.rs:56-66`) — so a field `test_records: PersistentSortedTable<TestRecord, _>`
produces a variant `TestRecord`.

### Step 3: the dispatch layer

`shoal-derive/src/traits/db.rs` is the file to read. It generates every method of
`ShoalDatabase` as a match over tables. For example, `handle`:

```rust
#query_ident::#variant_ident(query) => {
    match self.#field_ident.handle(meta, query).await {
        Some((client, query_id, response)) => {
            let wrapped = #response_ident::#variant_ident(response);
            Some((client, query_id, wrapped))
        }
        None => None,
    }
},
```

`shoal-derive/src/traits/db.rs:62-74`

and `load_partition`, which contains the ordering subtlety described in
[Query Execution](../tables/query-execution.md#resumption):

```rust
if let Some((unblocked, generation)) = self.#field_ident.load_partition(loaded_kinds.loaded).await {
    let mark_evict_msg = ServerMsg::MarkEvictable { generation, table, partitions: vec![id] };
    for (meta, unwrapped) in unblocked {
        shard_local_tx.send(ServerMsg::Query { meta, query: #query_ident::#variant_ident(unwrapped) }).await.unwrap();
    }
    shard_local_tx.send(mark_evict_msg).await.unwrap();
}
```

`shoal-derive/src/traits/db.rs:152-173`

Note this generated code calls `.unwrap()` on channel sends and refers to `shoal_core::` by
absolute path — so `shoal_core` must be resolvable at the call site, which it is via the
`shoal` façade's re-exports.

## Design notes

**The schema is the type system.** There is no catalog, no runtime type information, and no
dynamic dispatch on the query path — a `QueryKinds` match compiles to a jump table over table
variants, and each arm is monomorphised for a concrete row type. The trade-off is stark: every
schema change is a recompile of both server and client, and client and server binaries must
agree exactly ([Wire Protocol](../architecture/wire-protocol.md#limitations)).

**Codegen instead of trait objects.** The alternative — `Box<dyn Table>` — would allow runtime
table registration at the cost of virtual dispatch and lost monomorphisation, and would make
`MaybeLoaded<P>`'s zero-copy access much harder to express. Shoal chose codegen, and pays for
it in build times, in error messages that point into generated code, and in the 30-line
`where` clauses that appear whenever a human has to write the bounds by hand
(`shoal-core/src/server/tables/persistent/sorted.rs:118-149`).

**Generation, not a trait, unifies the table types.** Because the dispatch layer calls methods
by name rather than through a trait, the two persistent tables are not required to agree — see
[Table Types](../tables/table-types.md#the-asymmetry-that-matters) for what that has cost.

## Limitations

- Validation errors in the table derives are `panic!`s with no spans; only `#[db]` produces
  proper compile errors.
- Filters are equality-only and conjunctive.
- Generated code is hard to read in errors, and `cargo expand` is effectively required for
  debugging.
- `#[shoal_table(db = "...")]` is a string that must match a struct name, with no check until
  the generated identifier fails to resolve.
- `EphemeralTable` does not satisfy the interface the `#[db]` macro generates calls against, so
  it cannot appear in a database struct ([Table Types](../tables/table-types.md#ephemeraltable)).
- Generated code `.unwrap()`s on channel sends.
