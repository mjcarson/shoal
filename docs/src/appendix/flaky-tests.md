# Tests That Fail Under Load

A test that fails in a loaded run and passes when run again has failed nondeterministically. The
load schedules a fixture's processes late, so its waits run out, and the same lateness opens the
windows a race in the engine needs: many of this engine's races have only ever shown in a loaded
run. **This page records every such failure**, so that one that recurs is seen to recur, and an
assertion of what the system answered or holds is never put down to the load before its cause is
shown.

The record begins with F79's workspace run on 2026-10-11. From there to 2026-10-22 it is gathered
from the runs' logs, which are quoted where they were kept, and from the runs' notes in
[Test Coverage](test-coverage.md) where only a note was. What came before is in
[item 142](known-issues.md#142-two-fixture-tests-fail-intermittently-on-an-idle-host) and in those
notes. Since 2026-10-22 each run adds its own.

acknowledged write was an assertion that fired now and then.

## How a failure is recorded

1. **Every failure under load is entered.** That is a failure in a workspace run, or in any run
   beside load (the fixture at six threads, the rotational filter, a run beside a build), that
   passes when run again at three threads or alone. The test is the row, and each run adds itself
   to it with the message as the run printed it. A run whose log kept no message says so.
2. **Each is given a kind** ([below](#the-kinds)). An **Outcome** failure is a defect until its
   cause shows otherwise.
3. **Filing.** An Outcome failure is filed in [Known Issues](known-issues.md) at once, and any other
   kind at its second run. The item says what the assertion holds, which runs failed it, what is
   established, and what the next failure must keep to tell the causes apart.
4. **The record before this page** was triaged once, when the page was begun. Every row that had
   failed in two runs was filed, and so was every single failure that broke what the engine
   promises: a write answered unknown where it promises a name, a chunk gone, a refusal from a dead
   core. The other single failures are [listed below](#single-failures) and are filed at their
   next failure.
5. **Catch the next one.** A row's item names what to keep. The general means is a loop of the row
   beside the heaviest rows, keeping the child logs of every round that fails
   (`SHOAL_CHILD_LOG=$PWD/target/child-logs`, one row at a time: a whole suite under it writes tens
   of gigabytes), as item 142's rounds did
   ([#142 in round 16](../cluster-testing/correctness.md#142-in-round-16)).
6. **Leaving the page.** A row leaves when its item is resolved, or when its cause is shown to be
   the test's own and the test is changed. It moves to [Left the page](#left-the-page) with the
   change that ended it. A row that stops failing stays, and says since when.

## The kinds

- **Outcome.** The test asserted what the system answered, holds or did, and it was otherwise: a
  write answered unknown where the engine promises a name, a chunk gone, a move given up, a log
  written by a repeat. A defect until shown to be the test's.
- **Fixture.** The test's or the fixture's own race, shown by its source or its output: a read that
  races a commit, a correct refusal taken as a failure.
- **Deadline.** The test waited, with a bound, for something that had not come: a restore, a
  drain's releases, a move, a write's latency. A slow host and a stuck operation look alike here,
  and the row says which once they are told apart.
- **Setup.** The cluster the test starts never became what the test needs (no control quorum, a
  child not ready, voters not promoted, a setup write unanswered) before anything the test is about.
