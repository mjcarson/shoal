# Delivered Features

Capabilities that have been built, kept for the same reason [Resolved Issues](../appendix/resolved-issues.md)
are kept: the reasoning behind a feature is worth more than the feature. Each page states what
the thing does, the choices its design rests on, what was rejected on the way, what it still
cannot do, and — the part that matters when changing this code later — the invariants it depends
on.

Item numbers are prefixed `F` and are **never reused**, the same rule [Known
Issues](../appendix/known-issues.md) and [Optimizations](../appendix/optimizations.md) follow.

| # | Feature | What it does |
| --- | --- | --- |
| F1 | [Sort-key range predicates](sort-key-ranges.md) | A sorted get or exists can bound its rows by a range of sort keys instead of naming them, in memory and in an archive, which makes an exclusive lower bound a cursor and paging a large partition cost a page |
| F2 | [Projections on get queries](projections.md) | A get can ask to be answered with a named subset of a tables fields instead of whole rows, which reads only those fields out of an archive rather than deserializing every field of every row it returns |
| F3 | [A three layer performance harness](performance-harness.md) | Criterion micro-benchmarks, ~~the `tmdb` example~~ (a purpose-built workload since [F8](purpose-built-workloads.md)), and a working `hotpath` profile, captured into committed JSON and judged against a frozen baseline and a trailing one, so an optimization can be shown to have worked rather than argued to have |
| F4 | [Archives are validated once, not once per read](validated-archives.md) | A partition read off disk is validated when the read lands and held in a form that carries that fact, so a query against an evicted partition seeks it directly instead of re-running rkyv's validator over the whole buffer first — and the archived read path became reachable from a test for the first time |
| F5 | [The flushed sweep runs on a wakeup, not on every message](flushed-sweep-gate.md) | A shard asks "what is durable now?" when a write has landed or a log is due to rotate, instead of after every message it handles, which took that sweep from 711,638 calls to 21,279 in the same workload without moving when a rotation fires |
| F6 | [A per query stage breakdown](stage-breakdown.md) | Every query records when it reached each of nineteen points between the client's `send` and the response coming back, joined across client and server and reported as the mean breakdown of the queries at each latency rank — which showed the insert tail is `durable_write` and `durable_sync_wait`, and that the two stages the design suspected are 0.6% and 0.8% |
| F7 | [A benchmark runner that renders its own results](bench-runner.md) | The three bash scripts became a workspace crate that runs the benchmarks, records the commit, tree state, machine and toolchain each capture was taken on, compares the macro layer for the first time on whether two observed intervals are disjoint, filters benchmarks the way `cargo test` does, and generates the book's [Benchmark Results](../performance/overview.md) page with its charts and a per-layer staleness badge |
| F8 | [Purpose-built workloads, in the crate that judges them](purpose-built-workloads.md) | The `tmdb` example stopped being the benchmark: fifteen workloads now live in `shoal-bench` itself, each isolating one path, each generating its own rows from a seed so a clean checkout can reproduce the macro layer for the first time — which bought the first per-query service time this repository has produced, a resident-versus-archived control pair, and a fanout curve that puts a number on O13's quadratic term |
| F9 | [Ephemeral tables, and the benchmarks that need them](ephemeral-tables.md) | A table that keeps everything in memory is now declarable in a `#[db]` schema, after two years as a struct nothing could reach — as the same table every persistent database uses with a storage engine that writes nothing, so the two cannot drift apart; which made eight storage-free control workloads possible and let this repository state that durability is roughly 4× the write path rather than infer it from a profile |
| F10 | [Framing and protocol evolution](framing-and-protocol-evolution.md) | Every frame now opens with a version, a message type, two flag bytes and a bounded length, in a module rather than at four hardcoded call sites — which costs zero bytes because narrowing the length to a `u32` pays for the other three fields exactly; a connection opens with a handshake carrying a compile-time fingerprint of the schema each peer was built from, so two peers built from a reordered field refuse each other by name instead of exchanging archives; and a hostile length prefix now closes one connection where it used to panic a shard and every client on it |
| F11 | [The error channel](error-channel.md) | A query that failed can say so, and say which kind of failure it was, instead of answering `Get(None)` — the same answer an empty partition gives: `ResponseAction::Error` carries a pinned code and a line of prose, a frame level `Error` type carries the failures that cannot be a response at all, and between them a read that could not be made, a response too large to frame, and a connection that stopped being read all reach the client that was waiting on them rather than arriving as an empty result, a closed socket, or nothing at all |
| F12 | [Authentication](authentication.md) | A connection can say who it is, and a server can refuse one that will not: SCRAM-SHA-256 over the `Auth`/`AuthResponse` frames [F10](framing-and-protocol-evolution.md) reserved and never wired, negotiated in two bytes cut out of the handshake's reserved tails so nothing about the frame layout moved — the server holds a salted iterated derivation and never a password, an account that does not exist fails in the same words and the same number of round trips as a wrong password, the client checks the server's signature back, and a completed exchange yields the `Principal` that per-table authorization has been filed as blocked on. Off unless a config asks for it |
| F13 | [The transport workloads](transport-workloads.md) | The client is no longer the one layer whose total has never been bounded: eight workloads over the four ways a caller can reach a server — `send` with one query, `send` with many, `stream`, `stream_unordered` — each at a 256-byte row and at a MiB one. The size axis is the point rather than a completeness exercise: at 256 bytes the fixed per-response costs dominate and the four modes spread nearly 4×, at a MiB the per-byte costs dominate and all four collapse into one number, so a per-byte tax such as encryption is invisible in one regime and is the entire cost in the other. This is the precondition [D4](../direction/encryption.md) names for taking encryption at all, and what makes O28 and O30 adjudicable for the first time |
| F14 | [Encryption in transit](encryption-in-transit.md) | TLS 1.3 between a client and a shard, configured per listener and off by default. rustls performs the handshake and then hands the keys to the kernel, so the record layer is kTLS and the response read is **unchanged** — `TcpProxy`, `ShoalResponse` and both server relays did not have to learn that TLS exists, and the zero-copy property the branch is named for survives encryption. [D4](../direction/encryption.md) recommended rustls' unbuffered API instead, on the strength of documentation that says it lets the caller supply the buffers; the crate's source says plaintext comes out of a `Vec` rustls owns, so that option cost exactly the copy it was chosen to avoid. A spike settled the replacement before anything was built. Eight encrypted transport arms pair with the eight plaintext ones, which is the control pair D4 called a precondition — it exists now, and has not been captured |

The feature that looked like it already did this could never have worked: `pub mod server;` and `shared/traits.rs`'s glommio import were both unconditional, so turning it off produced a build failure rather than a client, and nothing had ever tried. `#[shoal::db(client)]` emits the half of a schema that talks to a database and not the half that is one; `split_by_shard` left the shared trait whose signature named the server's routing types; and generated code names `::shoal::` alone, which closes the body of item 54. Verified by a crate that declares no engine and fails to compile if one creeps back |
| F16 | [The client builder](client-builder.md) | Everything about a client that was a literal is now a setting, and a client can be told about more than one server. `Shoal::builder()` carries pool sizing, deadlines, credentials and TLS on one object, with `PoolConfig` and `Deadlines` defaulting to exactly the six numbers that were hardcoded — a test asserts all six, because making something configurable must not quietly reconfigure the callers who never asked. `ClientOptions` is absorbed rather than replaced, so the four call sites outside the crate do not move. One attempt to connect walks the whole endpoint list from a shared turn counter, and the unit tests pin that rather than the end-to-end behaviour — the integration test passes against a build with the loop stubbed out, because `bb8`'s retries plus the counter find a live server eventually, and "eventually" is bounded by the connection timeout the loop exists to protect. | F17 | [The workload grid](workload-grid.md) | Seventy-four workloads answering the question the isolating set structurally could not: **what a caller's own workload costs**. The read/write mixture is the first one anywhere in the repository: the harness had no mix knob at all, because [F8](purpose-built-workloads.md) had deliberately made reads and writes separate workloads so that neither could hide the other. That argument is about **attribution** and it still holds — a regression is attributed with the isolating pairs, never with a grid arm. YCSB's *specification* is adopted natively and its harness is not: `r50`/`r95`/`r100` are workloads A, B and C, the reference row is its 1 KiB record, and the Zipfian and recency generators are YCSB's own algorithms with YCSB's `theta = 0.99` and its FNV-1a scramble — so a number here reads next to a published one while a clean checkout still reproduces everything with nothing fetched. Every arm reports its read and write distributions apart, never pooled, and counts queries as well as rows. Everything a query does — its key, its width, whether it is a read — is a function of its **index** rather than of a generator walked forward, because a mixture is driven by several slots sharing one cursor and anything sequential would depend on which slot got there first |

| F23 | [The intent log's staging buffer sizes itself](self-sizing-staging-buffer.md) | [O34](../appendix/optimizations.md) said a record wider than the staging buffer gets one DMA write and one DMA allocation to itself, leaving the group commit below it nothing to group. `f22-row-size` measured that at **1.22×** on 64 KiB rows and corrected its shape at the same time: the gain is in how many records share an aligned write, not in whether the record fits — a buffer holding *two* 8 KiB records is worth nothing over one holding none, and eight is where it arrives. So the fix is a sizing rule rather than a larger constant. `latency_sensitive.buffer_size` becomes a floor, a new `max_buffer_size` becomes a ceiling, and between them `StreamWriter` sizes each buffer to hold about eight of the widest record the last one held — decaying from the last buffer rather than from a high-water mark, so one outlier costs one oversized buffer instead of pinning every buffer after it wide. A record wider than the ceiling still gets a buffer of its own, because records are never split across buffers and no configured ceiling may override the log's framing. Pinning the ceiling to the floor gives back the old allocation exactly, which is both the escape hatch for an operator with a memory budget and the control the tests are written against. Reproduced before it was fixed: a bundle of 128 rows of 8 KiB became 128 writes and 128 DMA allocations, and is now 16. **Captured** as `f23-staging-buffer`, on the prediction written down before it ran: the five `macro/conf/storage/latency_buffer/r50/w65536/*` rungs converge, since they now all resolve to the same ceiling. They did — the spread across them went 1.225× to **1.010×**, and the shipped `buffer_size: 4096` gained **+22.0%** at 64 KiB rows and +5.6% at 8 KiB on disjoint intervals, with the 1 KiB reference cell unmoved. The fix raised the badly set rungs to where the well set ones already were and left those alone, so what the 1.22× measured was the distance between a good setting and a bad one, and there is no longer a bad one at these widths. Neither `shoal.yml` nor anything under `shoal-bench/` was touched, on purpose: a field added to either would move the fingerprint of every workload and orphan the arms this is measured against |

## How a feature gets written down

Not every change earns a page. A bug fix gets one when it had a wrong mental model behind it; a
feature gets one when it introduced a model that was not there before, because the next person to
touch that code will reason from the model rather than from the diff. The sections are always the
same:

**Context** what was not possible, and why it mattered. **What it does**, across every front end
that can reach it. **Design choices** and **Alternatives rejected**, together, because a design is
only understandable next to what it is not. **Limitations**, so that the gap between what it looks
like and what it does is written down rather than discovered. **Invariants to uphold**, which is
the section to read before changing the code it describes. **Performance**, naming what got
cheaper and what did not. **Tests**, naming what fails if the feature is reverted.
| F24 | [Routing benchmarks](routing-benchmarks.md) | Routing is the hop every query takes between arriving on a socket and reaching the shards that can answer it, and it was the one layer of the query path with **no benchmark of any kind**. [TODOs](../appendix/todos.md) had asked for it since [F3](performance-harness.md) and twice recorded that nothing blocked it — `Ring::find_shard` and `split_by_shard` are pure CPU over plain data, needing no server, no executor and no storage backend — and it was left unbuilt for four more features anyway. Four groups: the key→shard lookup swept across ring sizes, ring construction, the multi-partition split swept across key counts, and a **write** beside it as the control, since a write names one partition whatever the get beside it named and so exercises the same function while being flat in the only thing that varies. Two findings. `find_shard` is **392 ps, flat to 0.4% across a 64× change in the ring** — the tablet ring answering in constant time, which is the whole property [Resolved #11/#12/#37](../appendix/resolved/tablet-ring.md) was built for and which nothing had ever checked. And splitting a get is **quadratic in the keys it names**: `group_by_shard` deduplicates by scanning every key already placed, so the *i*-th key walks the *i*−1 before it — 4.13 ns·n + 0.0109 ns·n², which is 14.5% of the split at 64 keys and 40% at 256. Filed as [O39](../appendix/optimizations.md), and filed with the argument against acting on it: the whole split at 256 keys is 1.77 µs against a read that costs 40, so removing the quadratic outright buys under 2% of the widest query anybody runs. **The thing worth more than either finding** is what it does to a curve already in use — `macro/fanout/n` is what [O13](../appendix/optimizations.md) is ranked on, O13 is *also* an O(n²) in the same caller-set *n* one layer later, so that curve has two quadratics under it and can attribute a bend to neither. Nobody had noticed, because nothing had ever looked at this layer |
| F25 | [Read buffers are filled, not zeroed](read-buffers-are-filled-not-zeroed.md) | Both ends of a round trip allocated a buffer, wrote zeroes over every byte of it, and then overwrote every one of those bytes with the read on the next line — [O29](../appendix/optimizations.md) on the server since [F10](framing-and-protocol-evolution.md) bounded the allocation beside it and left the zeroing, [O37](../appendix/optimizations.md) on the client, unfiled until the read path was walked in code. Neither is written twice now, and the two halves are fixed differently because the two runtimes force it: tokio's `ReadBuf` counts what a reader initialized, so the client's `set_len` is discharged by a **check**; `futures::io::AsyncRead` takes a `&mut [u8]` and reports nothing, so the server's is discharged **structurally** — a `RequestBody` whose field is private and whose only constructor is the read, which is what turns the buffer's initialization state from a property several call sites had to respect into one the type will not let them break. Two claims the entries made turned out to be wrong and are recorded beside them rather than in place of them: the memset was never in the `decode` stage, because `base` is stamped *after* the read and the whole body read therefore falls in `net_in` where no instrument separates it from wire time; and `BytesMut::zeroed` is `vec![0; len]`, which is calloc rather than an unconditional `memset`, so the asymptotic entry is the client's `AlignedVec::resize(len, 0)` and not the server's. Measured by a new pair of criterion groups that run **both shapes in one build**, so one capture adjudicates the change and the `zeroed` arms stay afterwards as controls for a shape neither end has. The capture it needed could not be committed until [Resolved #79](../appendix/resolved/micro-only-capture-current.md): `render` drew all eleven pages from one capture, chosen as the newest with a *micro* layer, so a `--layer micro` capture emptied the seven macro pages — which then said nothing had ever measured a read/write mixture while eleven macro captures sat in the same directory |
| F26 | [Requests are routed from the archive](archive-routed-requests.md) | A bundle of queries arrives as one rkyv archive and the coordinator turned the whole of it into owned Rust values before looking at any of it — [O1](../appendix/optimizations.md), filed against every `String`, `Vec` and filter in every query being allocated and copied out of a buffer that already held them readable. Writing the design pass it was blocked on found it was worse than the entry said: `split_by_shard`'s write arms end in `self.clone()`, and `SortedQuery::Insert { key, row }` carries the row, so **an insert's row was deep-copied twice** — both times on core 0, the single coordinator every request in the system passes through. At the 512 KiB end of the [row-size sweep](../performance/row-size.md) that is a megabyte of memory traffic per insert on the one core that cannot be scaled out of the way. The coordinator now deserializes nothing. It validates the bundle once, reads the partition keys and limit straight out of the archive — scalars sitting inline, no row ever touched — and hands each destination shard the buffer itself, as a `Bytes` whose clone is a refcount. The shard that answers a query is the shard that turns it back into one, and then narrows it. `RequestBody` gains a second and last exit, `freeze`, which keeps [F25](read-buffers-are-filled-not-zeroed.md)'s structural guarantee intact: only a body a read filled can be frozen. `ShoalDatabase::unarchive_queries` — written for exactly this and callerless since it was added — finally has its caller, and became `unsafe fn` on the way, because as a *safe* fn wrapping `access_unchecked` it let any caller hand it any bytes; what discharges it is that the coordinator validated the same immutable buffer first. `split_by_shard` is kept rather than deleted: it is no longer on the live path and it is the only definition of correct the new path has, so every test checks the two against each other and `routing/route_archived/*` is read against `routing/split_by_shard/*`. The per-query deserialize became a twentieth stage, `query_decode`, which is **not** a batch stage — so `decode` is no longer comparable across this change and a reader has to add the two together. Two things stated as limitations rather than discovered later: a fan-out get is now deserialized once per shard instead of once, which is close to a wash and not a saving; and sort-key normalization moved off the coordinator, contradicting a doc comment that said it happened once, which was corrected rather than left standing. **Not captured yet** — the prediction is written down first, and the claim that can fail is that `decode + query_decode` is *less* than today's `decode` on write-heavy arms |
