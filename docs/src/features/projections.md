# F2. Projections on get queries

A get could ask which rows it wanted. It could not ask which *parts* of them it wanted. Every get
answered with whole rows, so reading three fields of a wide row cost the whole row — deserialized
out of its archive, cloned into a response, sent over the wire, and walked by the client. A
projection is a named subset of a table's fields that a get can ask to be answered with instead.

## Context

`ResponseAction::Get(Option<Vec<T>>)` is parameterised by the table's row type, and both halves of
the scan produced that type and nothing else. `SortedPartition::collect_rows` pushed `row.clone()`;
its archived twin `collect_archived` called `R::deserialize(row)`. For a row that is mostly
`String`s, that deserialize is the dominant cost of a read: every string is allocated and copied out
of the archive whether or not the caller was going to look at it.

Two pages recorded the gap. `tables/query-execution.md` listed "rows are cloned into responses" under
its limitations, and `api/shql.md` said "Only `SELECT *`. There is no projection."

The TMDB example is the shape that motivated it. A `Movie` has fifteen fields, most of them strings
and vectors of strings; listing movies needs three of them. Before this, a list of a thousand movies
paid for fifteen thousand fields to show three thousand.

## What it does

**A projection is a struct that names a subset of a table's fields.** It is declared like a table
is, with rkyv derives written by hand and one shoal derive on top:

```rust
#[derive(Debug, Archive, Serialize, Deserialize, Clone, ShoalProjection, PartialEq)]
#[rkyv(derive(Debug))]
#[shoal_projection(table = "Movie")]
pub struct MovieSummary {
    #[shoal(partition)]
    pub id: u64,
    pub title: String,
    pub vote_average: f64,
}
```

**The database lists the projections each table has**, on the field holding that table:

```rust
#[shoal::db]
pub struct Tmdb {
    #[shoal(projections(MovieSummary))]
    pub movie: PersistentUnsortedTable<Movie, FileSystem>,
    pub movie_by_keyword: PersistentSortedTable<MovieByKeyword, FileSystem>,
}
```

**A typed get asks for one with `.projection::<P>()`**, and the response is retrieved as the
projection rather than as the row:

```rust
let response = client
    .send_one(MovieGet::new(vec![id]).limit(10).projection::<MovieSummary>())
    .await?;
let summaries = response.access::<MovieSummary>()?;   // &ArchivedVec<ArchivedMovieSummary>
```

The type parameter is what names the projection, so `.projection::<ReviewSource>()` on a movie get
is a compile error rather than a query that fails when it is answered.

**SHQL takes the projection name where the star goes.** `SELECT * FROM Movie` asks for whole rows;
`SELECT MovieSummary FROM Movie` asks for the projection. The grammar's first production changed
from a literal `*` to `projection := "*" | identifier`, and the completion menu offers the star plus
every projection in the database at that slot. Binding rejects a name no table declared, and a
projection belonging to a different table, with the offsets of the name it was given:

```
'ReviewSource' is not a projection of Movie. Its projections are: ["MovieSummary"]
```

**Everything else about a get is unchanged.** A projection decides what a row comes back as and
nothing about which rows come back, so filters, limits, sort keys, sort ranges, partition ordering
and disk loads all behave exactly as they did.

## Design choices

**A whole row is the identity projection of itself.** This is the choice the rest of the design
rests on. The table derive emits `impl ShoalProjection for Movie` whose `from_row` is a clone and
whose `from_archived` is the `R::deserialize` a get has always done. Every get path is then generic
over `P: ShoalProjection<Row = R>` and monomorphised, so an unprojected get compiles to what it
compiled to before and a projected one has no branch in its inner loop. There is exactly one scan,
not one per shape.

**A projection answers in its own `ResponseKinds` variant**, named after the projection type. This
is what keeps `shoal-core`'s response types untouched: `ResponseAction<T>`, `Response<T>`, `merge`,
`truncate` and `order_by_partitions` are already generic in `T`, so `Response<MovieSummary>` works
unchanged, and `FromShoal::retrieve` — which already matches `ArchivedResponseKinds::#name` — is
generated by calling the *existing* generator with the projection's ident. An archived enum is the
size of its largest variant and every `Response<P>` archives to the same size (a relative pointer
and a length), so the extra variants cost nothing on the wire.

**The projection travels as a unit enum on the get.** `SortedGet` and `UnsortedGet` carry
`projection: R::Projection`, a generated `{Row}Projection` enum whose default is `Full`. It is a
value rather than a type because the query crosses a wire; the type is recovered on the shard that
answers, by a match that runs once per query.

**The database macro generates the projection enum**, not the table derive. A table derive sees one
table and its own fields; only `#[db]` sees every projection of every table at once, and both the
enum and the response kinds need the whole set. That is also why the projections are declared on the
database's field rather than on the table.

**A projection carries its table's partition key.** The shard collecting the shares of a split get
puts the rows back in the order the query named their partitions in, and it does that by asking each
row which partition it came from. A projection that dropped the partition key would come back
shuffled. This is enforced two ways: the derive refuses a projection with no `#[shoal(partition)]`
field, and it emits a compile-time assertion that the projection's `PartitionKey` type is the same
type its row's is.

**A parked get is type-erased, and only a parked get.** A get whose partition has to be read from
disk keeps what it found so far in `PendingGets`, which is now a `HashMap<(Uuid, usize), Box<dyn
Any>>` because the rows in it can be any of the table's projections. The box is only ever allocated
where the old code already inserted into that map — on the pending path — so a get whose partitions
are all resident finishes in one execution and never touches it. A get that is waiting pays one
allocation and one downcast against a disk read it is already blocked on.

**A projection is a named type, not a column list.** `SELECT title, year FROM Movie` is still
rejected. The rows come back as an archive of a concrete type, so an arbitrary set of columns has no
type to be, and inventing one per query would mean giving up the zero-copy client.

## Alternatives rejected

**A per-table `Rows` enum inside `ResponseAction::Get`.** Instead of one response variant per
projection, `Get(Option<MovieRows>)` where `MovieRows` is `Full(Vec<Movie>) | Summary(Vec<MovieSummary>)`.
This puts a discriminant on every response including the unprojected ones, and forces an associated
type through rkyv's derive bounds — `#[rkyv(omit_bounds)]`, explicit serialize and deserialize
bounds, the lot — for no gain over a flat variant per projection.

**Projecting late, at reply time.** Keep the scan producing whole rows and drop the unwanted fields
just before `rkyv::to_bytes`. This is a much smaller change and gets the wire saving, but it gives up
the part that matters: the archived scan would still deserialize every field of every row it
returned, which is the cost a projection exists to avoid.

**A runtime registry of projection functions** (`inventory` or `linkme`), which would free `#[db]`
from knowing the set and let a projection be declared anywhere. It costs a dynamic call per row,
gives up the monomorphised inner loop, and produces bytes rather than a `Vec<P>` the client can
`access` — three things traded for one declaration site.

**Carrying per-partition row counts on the wire** so the gather interleaves shares by rank instead of
hashing each row's partition key. This would lift the requirement that a projection carry its
partition key, and would also drop `sort_by_cached_key` from every multi-partition get. It changes
the response shape and `FromShoal::retrieve`'s signature, so it is filed as
[O22](../appendix/optimizations.md) rather than done here.

**Dropping the partition key requirement by having the shard tag the rows.** Same idea, smaller: the
shard already knows which partition each batch came from, since `PendingGet` holds one slot per
partition key in query order. Rejected for the same reason — it is a change to the response shape,
and it belongs with O22.

## Limitations

- **A projection cannot be declared for an ephemeral table.** An `EphemeralTable` cannot be a field
  of a `#[db]` struct, so there is nowhere to declare one. Ephemeral tables carry an
  `ShoalProjection<Row = Self>` bound and answer with whole rows only.
- **A projection has to name its table's partition key**, and to name it in the same field order.
  The type check catches a mismatched key *type*; it cannot catch two `u64` fields swapped.
- **There is no column list in SHQL.** `SELECT a, b FROM T` is a parse error, not a query.
- **A projection is a separate type, so it has to be written out.** There is no `#[derive]` that
  turns a field list into one, and no way to ask for "everything but `data`".
- **`shoalctl` renders a projection through `TableRowFormat`**, which the derive generates for the
  projection's own fields. The table name it shows is still the table the rows came from, so two
  queries over one table can render different columns under the same heading.
- **A projection does not reduce what is read off disk.** A cold partition is still read whole;
  there is no per-column layout in an archive. The saving is deserialization, wire bytes, and the
  client's walk — the same honest caveat [F1](sort-key-ranges.md#performance) carries about ranges.
- **A get names one projection for all of its partitions.** There is no way to ask for whole rows
  from one partition and a projection from another in a single query; that is two queries.

## Invariants to uphold

- **`for_partitions` and `to_blocked` must copy the projection.** A get narrowed to a shard, or
  parked on a disk read, is rebuilt from the one that spawned it. Dropping the projection there
  makes a projected get answer in the wrong variant, which the client reads as the wrong type.
- **The identity projection must stay inlineable.** `from_row` is a clone and `from_archived` is a
  deserialize, both `#[inline]`. If either grows a branch or an indirection, every existing
  unprojected read pays for a feature it does not use.
- **A parked get resumes with the projection it started with.** `PendingGets::resume::<P>`
  downcasts, and panics rather than silently starting fresh, because starting fresh would discard
  the rows already found. This holds because the query parked on a partition is a copy of the one
  that parked it, and dispatch reads the projection off that copy.
- **A projection hashes its partition key the way its row does.** `order_by_partitions` looks each
  returned row's partition key up in a rank map built from the keys the query named. A projection
  that hashes to something else sorts last, silently.
- **Every response arm has to cover the projection variants.** `merge`, `truncate`,
  `order_by_partitions`, `get_index_archived`, `is_end_of_stream`, `get_query_id`, `succeeded`,
  `kind`, `get_exists`, `response_table_name` and `format_response` are all generated over the
  tables *and* their projections. A variant one of them misses is a projected get whose rows are
  quietly dropped on the gather path.
- **The limit is counted against rows found, not rows read.** `limit_reached` is generic in the
  element type for that reason — a projected get fills its limit with the same number of rows an
  unprojected one does, and it must not become cheaper to overrun.
- **`{Row}Projection::Full` must stay the `Default`.** A get that never named a projection gets it
  by construction, and so does every query that is not a get. That is what lets the database
  dispatch on one value instead of on the query kind as well.

## Performance

| Access | Before | After |
| --- | --- | --- |
| A projected get over an archived partition, *f* of *n* fields | *n* fields deserialized per row | *f* fields deserialized per row |
| A projected get over a resident partition | whole row cloned | projected fields cloned |
| An unprojected get, either kind | as before | **unchanged** — the identity projection inlines to the same code |
| Wire bytes for a projected response | every field | the projected fields |
| Client walk of a projected response | archived row type | archived projection type, zero-copy as before |
| Reading a cold partition | whole partition | whole partition, **unchanged** |
| Dispatching a get | one match on the query kind | one more match, per query, on the projection |

The last two rows are the ones to remember. A projection changes what is *deserialized* and what
crosses the wire; it does not change what is read off disk, and it adds one branch per query — not
per row.

A projection's `from_archived` shares one `rkyv::de::Pool` across the fields of a row rather than
building one per field, which is what `rkyv::deserialize` would do at each call site.
